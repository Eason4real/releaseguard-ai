# ReleaseGuard AI v7 诊断与改进验证报告

> 面向 AI 产品经理、产品负责人和研发负责人  
> 报告性质：Dev 阶段产品决策材料，不是 Holdout、生产准确率或对外宣传材料  
> 评测范围：v7 正式评测 22 案例 × 3 轮，共 66 次；追加 17 个代表案例的离线反事实实验

## 一、管理层结论

ReleaseGuard AI 目前不是“完全不可行”，但也远未达到自动根因判断产品的上线门槛。

v7 已经证明两件事：

1. 系统可以稳定完成调查流程。66/66 次正式运行技术执行成功，v4/v5 的空响应、非法 JSON 和结果丢失问题已经基本解决。
2. 系统目前无法稳定把已收集的证据转化成正确、可引用的最终诊断。正式 v7 只有 1/66 次形成明确诊断，严格根因得分仅 7/60（11.7%）。

随后进行的离线损失分解进一步证明，问题并不是模型完全不会调查，而是证据进入最终综合阶段时发生了严重损失：66 条轨迹中，46 条已经满足现有综合条件，41 条却因为 Synthesizer 输出契约或服务端校验失败而没有交付诊断。

在不重新调用任何调查工具、不向模型提供 Gold 的条件下，仅修复综合阶段的字段契约、错误反馈和缺失的公共说明后，17 个代表案例中有 15 个能够交付有效终态；其中 14 个可评分结果里，3 个严格正确、7 个部分正确、4 个错误。

因此，当前正确的产品判断是：

**ReleaseGuard 的“证据调查助手”方向可行；“自动根因判断器”仍未被证明。下一版应优先修复证据交付和综合契约，而不是重跑旧版本、无限增加 Prompt，或立即更换模型。**

## 二、用户现在实际会得到什么

从产品经理视角看，v7 的体验是：系统调查过程不再频繁崩溃，也确实调用了发布信息、产品指标、分群指标和用户反馈等工具，但大部分调查最终仍只返回“证据不足”。

这意味着用户能看到系统在工作，却无法获得足够明确的发布决策支持。对真实发布负责人而言，以下关键问题仍经常没有答案：

- 这次异常是否由刚刚上线的版本导致？
- 最可能的根因是什么？
- 哪些指标、用户群和地区受影响？
- 哪些替代假设已经被排除？
- 现在应该继续观察、暂停发布、回滚，还是升级人工调查？

当前产品适合内部 Alpha，用于汇总证据和辅助人工调查；不适合承诺自动归因，更不能自动触发回滚或外部处置。

## 三、正式 v7 表现

| 指标 | v7 结果 | 产品含义 |
| --- | ---: | --- |
| 技术完成率 | 66/66，100% | 调查链路稳定性已经达标 |
| 明确 FINALIZED | 1/66，1.5% | 几乎没有向用户交付明确诊断 |
| 旧口径业务完成率 | 22/66，33.3% | 部分内部证据存在，但口径高估用户价值 |
| 明确诊断且引用完整关键证据 | 1/66，1.5% | 真正可消费的结果极少 |
| 严格根因得分 | 7/60，11.7% | 准确识别完整根因的能力不足 |
| 宽松根因得分 | 7/60，11.7% | 正确方向也没有稳定传递到最终答案 |
| 内部关键证据召回 | 68.9% | Collector 并非没有找到信息 |
| 最终关键证据引用 | 5 项 | 大量证据没有进入用户答案 |
| EMPTY 工具调用 | 18/154，11.7% | 工具查询仍有浪费，但不是最大问题 |

这里最容易被误读的是“技术完成率 100%”。它只代表流程正常结束，不代表调查正确，也不代表用户得到了可执行结论。

## 四、问题到底出在哪里

### 1. 首要问题：综合阶段契约与校验不匹配

正式轨迹中，41/66 次出现 Synthesizer 输出或服务端校验失败。典型问题包括：

- Prompt 没有完整告诉模型 `LIMITATION` 类型需要额外字段；
- 第一次输出校验失败后，修复轮次只知道“输出不合法”，不知道具体错误码和字段位置；
- 某些诊断内容和证据引用已经完整，只因为遗漏公共 `rationale`，整条结果就被丢弃；
- 结构化修复次数有限，但反馈信息不足，导致模型重复同一个错误。

这些是 Harness 接口设计问题，不应归因于模型业务推理能力。

### 2. 第二问题：Evidence Packet 丢失了最有价值的信息

Collector 确实拿到了分群差异、指标数值、版本变化和用户反馈，但持久化 Evidence statement 经常只剩下“某工具返回了当前观察”这种通用描述。

真正有助于根因判断的内容，例如“9.2.0 为 0.61、9.1.4 为 0.94”“变更涉及 CheckoutConfirmation”，主要留在工具结果或 Evidence Assessment 的解释中，没有作为稳定、结构化的事实进入 Synthesizer。

这会导致模型知道“有一条指标证据”，却不知道证据具体说明了什么。

### 3. 第三问题：Collector 找到方向，但假设粒度不够准确

反事实实验的宽松命中明显高于严格命中，说明模型经常找对组件或因果方向，却没有说清完整机制和受影响对象。

这不是纯格式问题，也不能只靠放宽评分解决。下一版需要让 Collector 产生更可区分的假设，并主动寻找能够区分机制的证据。

### 4. Gate 偏保守，但不是最大故障源

此前怀疑 Readiness Gate 是主要瓶颈。完整损失分解后发现，46/66 条轨迹实际上已经进入或具备进入综合阶段的条件。只有 7 条是在综合阶段正常选择拒答。

Gate 仍应从二态改为四态，但优先级应排在综合契约和 Evidence Packet 之后。

### 5. 基础模型能力是次要变量，尚不能下最终结论

同一个模型、同一批冻结证据，在没有新增工具数据的情况下，仅修复接口就把代表案例的技术交付从 0/17 提高到 15/17，并恢复了大量部分正确结果。

这说明直接换模型并不是当前最优先动作。只有当证据包信息完整、结构契约稳定后，严格根因得分仍停滞，才有资格通过同证据、同 Prompt 的模型对照实验判断模型上限。

## 五、17 案例反事实实验说明

本次实验从 41 条综合失败轨迹中按案例去重，选择 17 个代表案例。它没有重新运行 Collector，没有调用任何调查工具，也没有让 Synthesizer 读取 Gold。

只进行了三项修复：

1. 补全 Synthesizer 的输出字段说明；
2. 把服务端校验错误码、字段路径和简短错误信息反馈给有界修复轮次；
3. 当一个决策只缺少公共 `rationale` 时，由服务端补充固定流程说明，不修改根因、假设、证据或处置建议。

| 指标 | 原 v7 代表轨迹 | 修复后 |
| --- | ---: | ---: |
| 技术可交付 | 0/17 | 15/17，88.2% |
| 严格正确（排除 N/A） | 1/15，6.7% | 3/14，21.4% |
| 宽松命中（排除 N/A） | 1/15，6.7% | 10/14，71.4% |
| 仍然技术失败 | 17/17 | 2/17 |

这组结果非常重要，但不能被包装成 v8 正式成绩。它只证明：修复综合接口能显著恢复原本已经存在的业务信号。严格正确率仍然只有 21.4%，说明 Evidence Packet 和假设质量必须继续改善。

## 六、产品是否值得继续做

建议继续，但应收缩阶段性承诺，并设置明确停止条件。

值得继续的理由：

- 技术可靠性已经从系统性失败提升到 100%；
- Collector 内部关键证据召回达到 68.9%；
- 不增加调查数据，仅修复综合接口就能恢复 71.4% 的宽松命中；
- 当前问题可以被拆分、度量和验证，不是不可解释的随机失败。

不能盲目乐观的理由：

- 正式 v7 的明确诊断交付只有 1.5%；
- 反事实严格正确率仍只有 21.4%；
- 评测全部来自同一 Dev 数据集，存在调参过拟合风险；
- 盲评使用同一模型家族，不等同于独立人工审核；
- 当前没有真实生产数据、企业数据接入和不可见 Holdout 证明。

## 七、v8 产品方案

### P0：升级 Evidence Packet

每条 Evidence 应包含安全、结构化的事实摘要，而不是通用占位文字。至少包括：

- 指标值、基线、变化方向、样本量和时间窗口；
- 分群维度及各分群差异；
- 发布版本、模块、Feature Flag 和 rollout；
- 用户反馈主题、数量和代表性样本；
- 当前事件与历史事故的明确区分；
- 对每个假设的支持、反证或中立关系。

仍然不能把完整探索 transcript、隐藏思维链、案例 ID 或 Gold 放入证据包。

### P0：稳定综合接口

- 保留完整 JSON schema 提示；
- 把具体 validation code 和 path 提供给最多一次有界修复；
- 单独记录首轮成功率、修复成功率和最终失败原因；
- 只允许服务端补充固定流程字段，绝不能自动补根因或证据；
- 所有 grounding 规则继续保持，不通过放宽引用要求换取好看成绩。

### P0：将 Readiness 改为四态

- `READY_FOR_CAUSAL`：证据足以输出明确因果诊断；
- `READY_FOR_BOUNDED_HYPOTHESIS`：只能输出领先假设、反证和置信等级；
- `READY_FOR_ABSTENTION`：客观不可归因，但必须交付已确认事实和缺失信息；
- `NEEDS_COLLECTION`：只有存在明确的高信息增益工具时才继续采集。

### P1：改进假设质量

- 假设必须包含组件、机制、受影响对象和可证伪条件；
- Collector 应优先查询能够区分两个竞争假设的数据；
- 相同证据同时支持多个假设时，不应重复综合；
- 历史相似事故只能帮助提出假设，不能成为当前根因证据。

### P1：重新定义用户价值

下一版不能只统计“是否 FINALIZED”，还要统计：

- 明确诊断交付率；
- 可行动拒答率；
- 已确认事实完整率；
- 反证覆盖率；
- 关键证据最终引用率；
- 推荐下一步数据源的准确性；
- 人工是否能基于输出做出发布决策。

## 八、v8 的分阶段验证门槛

不要立即运行完整 3×22。建议按以下顺序推进：

1. 单元与契约测试：结构化输出、错误反馈、Evidence Packet 和 grounding 全部通过。
2. 17 案例 smoke：技术成功率至少 97%，严格根因至少 35%，宽松命中至少 65%。
3. 只有 smoke 达标，才冻结 v8 源码身份并运行正式 3×22。
4. 正式 Dev 目标：技术完成率至少 97%，业务完成率至少 60%，严格根因至少 50%，关键证据召回至少 85%。
5. Dev 达标后建立不可见 Holdout，并安排独立人工复核；在此之前不宣称生产准确率。

## 九、停止条件

出现以下任一情况，应暂停继续堆版本：

- Evidence Packet 升级后，17 案例严格根因仍低于 35%；
- 同证据包模型对照显示更强模型也没有显著提升；
- 关键根因所需信息根本无法由当前工具获得；
- Holdout 表现明显低于 Dev，证明改进主要来自过拟合；
- 单次调查成本或延迟超过目标，而准确率没有同步提升。

届时产品应明确定位为“调查证据工作台”，不再追求自动根因判断。

## 十、建议的产品决策

建议批准一个受控的 v8 研发周期，但不批准直接进行全量正式评测。

v8 的唯一核心目标是：**让已经找到的证据以完整、结构化、可引用的方式进入最终判断，并证明严格根因质量真实提升。**

在 smoke 门槛通过之前，不增加新模型、不扩充无关工具、不调整评分规则、不删除失败案例，也不对外宣传自动归因能力。

当前最合理的商业定位仍是：面向发布负责人的 AI 调查助手，帮助汇总证据、维护竞争假设、指出缺失信息并提供受控决策建议。自动根因判断是待验证能力，不是已完成能力。

## 附录：可信度边界

- 正式 v7：22 个受治理 Dev 案例，每案 3 轮，共 66 次。
- 离线反事实：17 个去重代表案例，不是新版本正式评测。
- 所有正式失败均保留在原始结果中，没有重跑覆盖。
- Synthesizer 不读取 Gold；Gold 仅在模型输出完成后由评分与盲评进程使用。
- 首批诊断性盲评因 Provider 要求 Prompt 显式包含 `JSON` 而出现 17 次 HTTP 400；失败尝试完整保留，修复后另存成功结果。
- 本报告不能证明真实企业环境表现，也不能替代人工安全评审。
