# ReleaseGuard AI Harness v2 产品评测报告

> 面向 AI 产品经理、产品负责人和项目决策者  
> 评测性质：同一套 Dev 案例上的版本对比，不是生产环境准确率，也不是不可见 Holdout 测试

## 先说结论

Harness v2 是一次有效的基础能力升级，但还不是一次足以让 Agent 独立承担发布决策的产品跃迁。

它最明显地解决了“系统经常跑不完”的问题：技术完成率从 v1 的 65.1% 提升到 93.9%。这意味着用户发起一次调查后，系统不再频繁因为接口波动、断点丢失或调用失败而直接中断。

但“能跑完”不等于“能给出有用结论”。v2 的业务完成率只有 36.4%，严格根因正确率为 28.8%。换句话说，在 66 次调查中：

- 62 次能够完成技术执行；
- 24 次既完成执行，又形成了满足关键证据要求的诊断；
- 19 次给出了与标准根因高度一致的答案；
- 33 次最终选择了 `INCONCLUSIVE`，即收集了一些信息，但没有形成明确结论；
- 4 次仍发生技术失败。

因此，当前适合的产品定位是：

**可供内部产品团队试用的“发布调查助手”，而不是可以独立作出发布归因或回滚决策的自动化 Agent。**

## 一、v2 到底改善了什么

| 产品问题 | v1 表现 | v2 表现 | 产品含义 |
| --- | ---: | ---: | --- |
| 调查能否正常跑完 | 65.1% | 93.9% | 从“经常中断”提升到“多数情况下可用” |
| 能否形成可交付的业务结论 | 18.2% | 36.4% | 提升明显，但仍只有约三分之一调查真正帮用户完成任务 |
| 根因是否高度准确 | 13.6% | 28.8% | 翻倍，但仍不足以支撑自动决策 |
| 根因方向是否至少部分正确 | 30.3% | 47.0% | 接近一半调查能给出正确方向或组件 |
| 是否找到了关键证据 | 38.9% | 68.9% | Agent 更容易找到决定性信息，但仍会遗漏约三成关键证据 |
| 无信息工具调用占比 | 58.9% | 54.4% | 仅小幅改善，超过一半工具调用仍没有带来新信息 |

这说明 v2 的主要价值不是“突然变聪明”，而是完成了三个更基础的产品能力建设：

1. **调查过程更可靠。** 短暂的接口或网络问题不再轻易毁掉整次调查。
2. **长任务可以续跑。** 余额或进程中断后，系统能从已验证的断点继续，不需要重做前面的案例。
3. **Agent 更清楚数据工具能查什么。** 当查询方式不匹配时，Harness 会提示可用的指标和分析维度，减少盲目试错。

这三项改进对产品化非常重要，因为它们解决的是“用户是否敢把一次耗时数分钟的调查交给系统”的信任基础。

## 二、用户实际会感受到什么

### 正向体验

用户最明显的感知会是：调查不再频繁半途消失，失败后也不用从头开始。

Agent 找到关键证据的能力从 38.9% 提升到 68.9%，因此用户更可能看到与异常指标、受影响用户群和发布变更相关的证据，而不是只得到一段泛泛解释。

所有被引用的证据 ID 都能对应到真实工具结果，引用有效率是 100%。这意味着 v2 没有为了提高答案率而放松证据边界，也没有用不存在的证据包装结论。

### 仍然明显的负向体验

一半调查最终仍是 `INCONCLUSIVE`。从用户视角看，这通常意味着：等待约 3 到 5 分钟后，Agent 给出了调查过程和若干可能性，却没有回答“这次发布到底是不是原因”。

工具调用中有 54.4% 返回 `EMPTY`。这并不是系统报错，而是 Agent 查询了一个没有信息增益的方向。用户不会看到底层每一次空查询，但会感受到调查慢、结论弱、Agent 像是在绕路。

v2 的单次调查中位耗时约 185 秒，P95 约 327 秒。对异步后台调查可以接受，但对需要 PM 在页面上等待的同步流程偏慢。

## 三、为什么技术完成率很高，业务完成率却不高

这是本次评测最重要的产品结论。

技术完成率 93.9% 只说明 AgentLoop、模型调用和工具调用最终没有崩溃。业务完成率 36.4% 才回答：Agent 是否形成了诊断，并找齐支撑该诊断的关键证据。

两者之间相差 57.5 个百分点，说明当前主要瓶颈已经从“基础设施可靠性”转向“调查策略和证据决策质量”。

具体表现为：

- Agent 能调用工具，但不总能优先选择最有判别力的查询；
- 遇到一次空结果后，仍可能在相似方向继续尝试；
- 找到部分证据后，不知道证据是否已经足够形成结论；
- 对不确定性的处理偏保守，容易停在 `INCONCLUSIVE`；
- 少数长轨迹在最后阶段仍可能输出不合格的结构化结果。

所以，下一版不应继续把主要精力放在“多加几次重试”或“允许更多模型调用”。更长的调查不一定更好，反而可能增加成本和空查询。

## 四、为什么 Direct LLM 分数更高，却不能直接替代 Agent

在这套离线 Dev 评测中，Direct LLM 的严格根因得分为 72.7%，明显高于 Harness v2 的 28.8%。这个差距必须正面承认。

但两者完成的任务并不完全相同：

- Direct LLM 一开始就拿到所有允许的静态观察，然后一次性回答；
- Agent 需要自己决定查什么、按什么顺序查、如何处理空结果、何时停止，并保留可审计轨迹；
- Agent 还受到证据、工具、审批和外部写入安全边界的约束。

因此，Direct LLM 更像是“给齐材料后的分析能力上限”，Harness v2 更像是“从有限线索开始自主调查的产品能力”。

产品上不应把 Direct LLM 替换 Agent，也不应忽略它的领先优势。更合理的做法是：

1. 将 Direct LLM 作为持续对照组，防止 Agent 编排越做越复杂但质量反而下降。
2. 研究如何让 Agent 更快获得真正相关的证据，而不是简单增加调用次数。
3. 在 Agent 形成证据包后，可考虑增加一次受约束的综合判断步骤，但不能绕过证据和审批边界。

## 五、现在能不能上线

### 可以做的

建议进入**内部 Alpha / 设计合作伙伴试用**阶段，适合以下场景：

- PM 或 Release Owner 主动发起一次发布异常调查；
- Agent 在后台运行，用户可以稍后回来查看结果；
- 输出明确区分“已证实”“可能”“证据不足”；
- 最终归因和回滚、发 Issue 等动作仍由人确认；
- 产品完整展示证据来源和调查轨迹。

### 暂时不应该做的

当前不建议：

- 对外宣传 80% 或 90% 的根因准确率；
- 自动判断某次发布就是根因并直接触发回滚；
- 隐藏 `INCONCLUSIVE`，用模糊话术包装成成功；
- 把这次 Dev 集结果称为生产环境准确率；
- 用更多重试或删除失败案例来提高表面数字。

### 建议的产品状态

| 产品阶段 | 建议 |
| --- | --- |
| 内部演示 | 可以 |
| 内部真实工作流试用 | 可以，但必须人工确认 |
| 设计合作伙伴试点 | 可以，需明确 Beta 边界 |
| 大规模公开 Beta | 暂不建议 |
| 自动归因或自动处置 | 不建议 |

## 六、下一版最应该优先做什么

### P0：减少无效调查，让 Agent 更快找到决定性证据

当前 329 次工具调用中有 179 次没有新增信息。下一版应优先降低 EMPTY 比例，而不是增加工具预算。

产品方案：

- 工具返回空结果时，明确区分“查不到数据”“当前工具不支持这种查询”“查询参数不匹配”；
- 记录已经失败的查询方向，禁止语义相同的重复尝试；
- 让 Agent 在每次调用前说明“这个结果将区分哪两个假设”；
- 连续两次没有信息增益时，强制重新规划或停止；
- 将真实可用的指标、维度和时间范围以能力清单形式提供给 Agent。

建议下一版验收目标：EMPTY 工具调用从 54.4% 降到 35% 以下。

### P0：建立“证据够不够”的明确协议

当前 Agent 即使找到部分关键证据，也经常不知道是否应该形成结论。

产品方案：

- 在形成诊断前，要求明确列出支持证据、反证和仍缺失的关键证据；
- 对发布回归、配置错误、上游依赖等不同事故类型定义最低证据组合；
- 当证据只支持相关性而非因果性时，禁止输出确定根因；
- 当证据已经满足最低要求时，避免继续无意义探索；
- `INCONCLUSIVE` 必须告诉用户还缺什么，以及下一步由谁补充。

建议下一版验收目标：业务完成率提升到 55% 以上，关键证据召回达到 80% 以上。

### P1：改善最终判断质量，而不是只改善流程成功率

产品方案：

- 在证据收集结束后增加一次“证据包综合判断”，只允许引用已收集证据；
- 强制比较最强的两个竞争假设，而不是只扩写当前领先假设；
- 对最终结论做机制、受影响对象和时间关系三项完整性检查；
- 对长轨迹的结构化输出失败增加更轻量的最终格式校验。

建议下一版验收目标：严格根因得分达到 45% 以上，宽松根因得分达到 60% 以上。

### P1：把等待体验改成异步任务体验

当前中位耗时约 3.1 分钟，P95 约 5.4 分钟。产品不应让用户盯着加载状态等待。

建议：

- 发起调查后允许离开页面；
- 展示当前阶段，而不是展示无意义的旋转动画；
- 完成后通过应用内通知提醒；
- 明确显示已花费时间、已使用工具和当前证据数量；
- 支持用户在 `INCONCLUSIVE` 后补充信息并继续同一调查。

建议下一版验收目标：P95 降到 4 分钟以内，或完整提供异步体验。

## 七、下一阶段建议使用的产品指标

下一轮不应只盯一个“准确率”，建议使用以下产品指标组合：

| 指标 | 当前 v2 | 下一阶段门槛 | 为什么重要 |
| --- | ---: | ---: | --- |
| 技术完成率 | 93.9% | ≥95% | 用户任务不能因为系统问题消失 |
| 业务完成率 | 36.4% | ≥55% | 衡量是否真的交付可用诊断 |
| 严格根因得分 | 28.8% | ≥45% | 衡量结论是否真正正确 |
| 宽松根因得分 | 47.0% | ≥60% | 衡量是否至少找到正确方向 |
| 关键证据召回 | 68.9% | ≥80% | 防止结论建立在不完整证据上 |
| EMPTY 工具比例 | 54.4% | ≤35% | 直接影响速度、成本和调查质量 |
| 三轮终态一致性 | 50.0% | ≥70% | 同一问题不应每次给出完全不同状态 |
| P95 耗时 | 327 秒 | ≤240 秒 | 决定交互方式和用户耐心 |

80–90% 的严格根因准确率可以作为长期目标，但不应作为下一版承诺。现阶段更合理的路线是先达到 45% 严格得分和 55% 业务完成率，再通过独立 Holdout 验证是否真正泛化。

## 八、投入产出判断

本次 v2 值得保留，因为它把系统从“经常跑不完”推进到了“多数调查可以稳定执行”，并且没有牺牲证据引用和安全边界。

但继续投入的重点必须转移：

- 不再主要投资传输重试和运行稳定性；
- 转向查询规划、证据充分性、停止规则和最终综合判断；
- 同时建立独立 Holdout，避免只在同一 Dev 集上持续优化；
- 保留 Direct LLM 作为质量对照和能力上限。

如果下一版仍只提高技术完成率，而业务完成和严格根因得分没有同步提高，就不应继续增加 Harness 复杂度。

## 九、给决策者的一句话版本

**Harness v2 已经让 ReleaseGuard Agent 基本“能稳定工作”，但还没有让它“稳定做对工作”。下一阶段应该从工程可靠性优化转向调查策略和证据决策质量优化，并继续坚持人工审批和可审计边界。**

## 附录：评测边界

- 本次使用 22 个受治理离线案例，每个案例运行 3 次，共 66 次。
- 数据包含 16 个合成案例和 6 个仓库原生案例。
- v2 盲评覆盖 66/66 个输出，但使用同一模型家族，不是独立人工评审。
- 误配置运行和余额耗尽运行单独归档，不进入正式 v2 分母。
- 所有正式失败都保留，没有删除失败案例或选择性汇报。
- Gold 只用于评分，不提供给 Agent 执行。
- AgentLoop、证据约束、审批和外部写入安全边界没有放宽。
