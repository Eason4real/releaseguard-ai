# ReleaseGuard AI 外部技术会诊提示词

你现在是一名资深 AI Agent 架构师、LLM 评测工程师和 B2B AI 产品负责人。请对下面项目进行独立、批判性的技术会诊。不要默认现有方案正确，也不要只给“优化 Prompt、增加数据、换更强模型”之类泛泛建议。请根据已有数据判断产品是否可行、主要瓶颈在哪里，以及下一步最值得验证的技术方案。

## 一、产品目标

ReleaseGuard AI 是面向产品经理、产品负责人和发布负责人的 Release Investigation Copilot。它在版本发布后出现指标异常时：

1. 读取发布信息、产品指标、用户分群、用户反馈和相似历史事故；
2. 维护多个竞争假设；
3. 调用只读工具收集支持与反对证据；
4. 输出有证据引用的根因判断，或明确说明证据不足；
5. 提议后续动作，但任何外部写操作都必须经过人工审批。

它不是通用 SRE Agent，也不允许自动回滚、绕过审批或无证据归因。

## 二、现有架构与安全边界

- 单 Agent、服务端 `AgentLoop`，不是 Multi-Agent。
- Planner 每轮只能返回结构化决策：创建假设、评估证据、调用工具、询问用户、最终诊断或停止并报告不确定。
- 服务端掌握状态、工具白名单、参数校验、预算、重复调用检测、持久化和审批。
- `ToolResult` 严格区分 `SUCCESS`、`EMPTY`、`ERROR`；只有有效结果才能形成 Evidence。
- Evidence 必须保留来源、强度、时间、工具结果关系和 provenance。
- 最终 Diagnosis Claim 必须引用当前调查中真实持久化的 Evidence。
- 历史相似事故只能用于形成假设，不能单独证明当前事故根因。
- Gold 仅在 Agent 完成后用于评分和盲评，绝不提供给 Agent。
- 禁止按案例 ID 硬编码、删除失败案例或放宽 grounding 换取指标。

## 三、评测设计

- 22 个受治理 Dev 案例，每版计划运行 3 轮，共 66 次。
- 同一冻结数据集、模型和基本预算进行版本对比。
- 指标包括：技术完成率、业务完成率、严格/宽松根因得分、关键证据召回、EMPTY 工具比例、三轮一致性、延迟、tokens、成本和错误。
- 盲评隐藏系统身份并随机化输出顺序，但当前使用同一模型家族担任 Judge，因此不是完全独立的人类评审。
- 这些是 Dev 数据，不是 Holdout，也不能宣称生产准确率。

## 四、最可信的正式结果：v3

v3 共 66 次完整评测：

| 指标 | v2 | v3 |
| --- | ---: | ---: |
| 技术完成率 | 93.9% | 93.9% |
| 业务完成率 | 36.4% | 47.0% |
| 严格根因得分 | 28.8% | 36.4% |
| 宽松根因得分 | 47.0% | 56.1% |
| 关键证据召回 | 68.9% | 75.3% |
| EMPTY 工具调用率 | 54.4% | 17.2% |
| 三轮终态一致性 | 50.0% | 54.5% |
| 三轮根因评分一致性 | 未列出 | 40.9% |

v3 终态：44 次 FINALIZED、18 次 INCONCLUSIVE、4 次 FAILED。单次调查 P50 为 154 秒，P95 为 299.4 秒。v3 的主要改进来自工具能力契约、参数规范化、EMPTY 原因分类和无信息停止预算。

## 五、v4、v5、v6 的情况

### v4

目标是增加证据充分性协议、证据收集/综合判断阶段、查询价值分级和更明确的不确定性分类。

但 v4 不是有效正式评测：第 1 轮缺失，只保留第 2、3 轮；大量模型响应最终 `content` 为空，引发 `INVALID_JSON`；评测期间源码内容哈希又发生漂移，因此没有盲评，也没有把 44 次结果包装成正式业务指标。

进一步发现 v4 的策略分支没有正确继承 v3 已验证的查询策略，这是版本组合错误。

### v5

v5 恢复 v3 查询策略，并尝试在空 JSON repair 时关闭 thinking。但实现只是省略 `thinking` 字段。4 个案例全部复现空响应后主动早停。

最小 provider 探针证明：对当前 `deepseek-v4-flash` 接口，省略 `thinking` 并不会关闭推理；必须显式发送 `thinking: {"type":"disabled"}`。

### v6

v6 显式关闭空 JSON repair 请求的 thinking，并继续保留 v3 查询策略与 v4 证据包协议。静态和回归测试已通过。当前仍在第 1 轮早期：前 7 个案例中 6 个技术完成、1 个技术失败；终态主要偏向 INCONCLUSIVE。样本不足，不能宣称效果提升。

## 六、当前核心困境

1. v3 工具效率和证据覆盖明显改善，但严格根因只有 36.4%，三轮根因一致性只有 40.9%。
2. 更复杂的证据协议和 Prompt 容易增加模型结构化输出负担，甚至导致技术稳定性退化。
3. 系统需要在“证据不足时谨慎停止”和“不要过度 INCONCLUSIVE”之间平衡。
4. 现有模型可能擅长收集整理证据，却不够稳定地完成最终因果综合判断。
5. 当前业务评测强调根因命中，但尚未充分测量调查耗时节省、人工采纳率、证据遗漏减少和错误建议拦截率。
6. 持续在同一套 22 个 Dev 案例上调参会产生过拟合风险。
7. 不能通过读取 Gold、放宽引用、删除失败或将 Dev 冒充 Holdout 来解决问题。

## 七、请回答的问题

请明确回答，而不是回避做判断：

1. 这个产品在什么产品边界下可行？哪些目标在当前模型条件下不可行？
2. 根据现有数据，瓶颈应如何归因到 Harness/AgentLoop、Prompt、工具与数据契约、基础模型能力、评测设计和产品定位？请给出大致贡献比例及依据。
3. v3 到 v6 的技术路线中，哪些设计应保留、删除或重构？
4. 是否应继续使用“一次模型同时负责工具规划、证据评估和最终综合”，还是拆成确定性状态机加两个独立 LLM 阶段？请给出具体架构。
5. 如何降低 schema repair、空响应和 Prompt 复杂度，同时不放宽 grounding？
6. 如何定义可执行的证据充分性协议，避免过度 FINALIZE 和过度 INCONCLUSIVE？
7. 是否应该换模型、使用不同模型分别负责 Planner/Synthesizer/Judge，或采用 constrained decoding？请说明最小实验矩阵和成本控制方式。
8. 下一版最值得做的 3–5 项改动是什么？每项说明假设、实现、验证方式、成功门槛、失败时结论和副作用。
9. 应该新增哪些产品指标，才能判断它作为 Copilot 是否有真实价值，而不只看根因正确率？
10. 在什么条件下应该停止继续开发，认定当前方案不具备商业可行性？

## 八、输出格式

请按以下结构输出：

1. **执行结论**：不超过 300 字，明确给出“继续、转向还是停止”。
2. **根因归因表**：因素、贡献比例、证据、置信度、可控性。
3. **目标产品边界**：可承诺、不可承诺、必须人工确认的事项。
4. **推荐架构**：组件、职责、状态流、模型调用点和确定性校验点。
5. **下一版实施清单**：按 P0/P1/P2 排序，必须具体到可验证行为。
6. **最小实验矩阵**：变量、对照组、样本、指标、停止规则和预算上限。
7. **风险与反对意见**：主动指出方案最可能失败的地方。
8. **Go/No-Go 门槛**：给出明确数值或可观察条件。

请区分事实、推断和假设。不要伪造缺失数据，也不要建议读取 Gold 或针对案例硬编码。
