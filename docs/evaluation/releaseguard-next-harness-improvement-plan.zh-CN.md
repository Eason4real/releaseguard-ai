# ReleaseGuard AI 下一版 Harness 完整改善报告

> 建议版本名：Harness v3（内部实验版本）  
> 报告对象：AI 产品经理、Agent 产品负责人、评测负责人、研发负责人  
> 当前基线：Harness v2 正式 Dev 评测，22 个案例 × 3 轮，共 66 次试验  
> 本报告是改善方案，不代表其中功能已经实现或指标已经达到

## 一、执行摘要

Harness v2 已经基本解决“Agent 经常跑不完”的问题，但还没有解决“Agent 能否稳定给出正确、有证据的业务结论”。

当前调查漏斗如下：

| 调查阶段 | 数量 | 占 66 次试验比例 | 产品解释 |
| --- | ---: | ---: | --- |
| 发起调查 | 66 | 100% | 全部正式试验 |
| 技术执行完成 | 62 | 93.9% | AgentLoop、模型和工具没有以错误结束 |
| 形成明确终态 `FINALIZED` | 29 | 43.9% | Agent 愿意给出最终诊断 |
| 达成业务完成 | 24 | 36.4% | 有诊断，并找齐规定的关键证据 |
| 严格根因正确 | 19 | 28.8% | 机制、对象和因果方向与标准答案高度一致 |
| 证据不足 `INCONCLUSIVE` | 33 | 50.0% | 调查跑完，但没有形成确定诊断 |
| 技术失败 | 4 | 6.1% | 结构化响应或遥测处理失败 |

下一版的核心任务不是继续堆重试或增加模型调用次数，而是提高每次调用的信息价值，让 Agent 知道：

1. 哪个查询最能区分当前竞争假设；
2. 一次空查询到底是无数据、参数不支持，还是方向错误；
3. 当前证据是否已经足够形成结论；
4. 还缺什么证据，以及是否值得继续查；
5. 什么时候应该明确结束，而不是无限探索或过早 `INCONCLUSIVE`。

建议将下一版定义为一次“调查决策质量升级”，而不是“运行可靠性升级”。

## 二、下一版的产品目标

### 北极星指标

**业务完成率**作为下一版北极星指标。

业务完成不是“程序执行成功”，而是一次调查同时满足：

- 没有技术失败；
- 形成了明确诊断；
- 找到了该案例要求的关键证据；
- 最终结论引用的证据真实存在；
- 没有绕过证据 grounding 和审批边界。

### 目标指标

| 指标 | Harness v2 | 下一版目标 | 最低发布门槛 |
| --- | ---: | ---: | ---: |
| 技术完成率 | 93.9% | ≥97% | ≥95% |
| 业务完成率 | 36.4% | ≥60% | ≥55% |
| 严格根因得分 | 28.8% | ≥50% | ≥45% |
| 宽松根因得分 | 47.0% | ≥65% | ≥60% |
| 关键证据召回 | 68.9% | ≥85% | ≥80% |
| EMPTY 工具调用比例 | 54.4% | ≤30% | ≤35% |
| 三轮终态一致性 | 50.0% | ≥75% | ≥70% |
| 三轮根因得分一致性 | 59.1% | ≥75% | ≥70% |
| P95 调查耗时 | 327 秒 | ≤210 秒 | ≤240 秒 |
| 引用 ID 有效率 | 100% | 100% | 100% |
| 审批/外部写入安全回归 | 0 | 0 | 0 |

这些目标是下一阶段门槛，不是对外承诺。只有在独立 Holdout 上复现后，才可以讨论生产能力声明。

## 三、问题诊断与优先级

### P0-1：超过一半工具调用没有信息增益

v2 共执行 329 次工具调用，其中 179 次返回 `EMPTY`，占 54.4%。

`EMPTY` 不是系统错误，而是本次查询没有产生可用观察。它可能来自四种完全不同的情况：

1. 查询参数格式不正确；
2. 当前工具不支持该指标、维度或过滤条件；
3. 数据存在，但当前时间范围或分群没有记录；
4. 该调查方向本身没有信息。

目前 Agent 对这四种情况的处理不够区分，容易在错误方向继续尝试，导致耗时增加、成本增加、证据召回反而不稳定。

### P0-2：Agent 不知道“证据是否已经够了”

关键证据召回已达到 68.9%，但业务完成率只有 36.4%。这说明 Agent 经常找到部分关键证据，却没有形成足够完整的证据组合。

当前缺少一个明确的证据充分性协议：

- 哪些证据只能证明相关性；
- 哪些证据能支持因果机制；
- 是否已经检查了反证；
- 是否确认了受影响对象；
- 对不同事故类型，最低证据组合是什么；
- 何时应该 `FINALIZE`，何时应该 `INCONCLUSIVE`。

### P0-3：调查停止规则不稳定

同一案例运行三次时，只有 50% 的案例得到一致终态。部分运行会 `FINALIZED`，另一些运行会 `INCONCLUSIVE`。

这意味着 Agent 的停止决策过度依赖单次模型输出，而不是由可解释的运行时规则约束。

主要风险包括：

- 找到足够证据后仍继续探索；
- 连续空查询后仍不改变方向；
- 证据不足时过早选择一个根因；
- 已经有明确领先假设时仍因措辞保守而停止为 `INCONCLUSIVE`；
- 在预算末尾才尝试形成诊断，最终结构化输出失败。

### P1-1：最终输出仍存在尾部失败

v2 有 3 次 `PROVIDER_MALFORMED_RESPONSE`，另有 1 次 token 遥测完整性错误。

虽然只有 4/66，但这些失败通常发生在已经执行较长调查之后。对用户而言，这是最差体验：等待数分钟、消耗大量调用，最后没有结果。

### P1-2：同步等待体验不适合 3–5 分钟任务

v2 的 P50 为 185 秒，P95 为 327 秒。即使后端质量改善，用户也不应该在页面上持续等待。

下一版需要同时优化真实耗时和等待体验，但必须明确：异步体验只能改善感知，不能替代调查质量提升。

### P1-3：当前评测无法证明泛化能力

v2 使用的是开发期间可见的同一 Dev 数据集，包含 16 个合成案例和 6 个仓库原生案例。盲评使用同一模型家族，也不是人工审核。

如果继续只在同一 22 个案例上迭代，会出现“越来越适应该数据集，但不一定适应真实新问题”的风险。

## 四、改善方案 A：查询信息增益系统

### 目标

将 Agent 的工具选择从“尝试一个可能相关的查询”升级为“选择最能区分竞争假设的下一步查询”。

### A1. 标准化工具能力清单

每个只读工具应向 Planner 暴露统一的能力描述：

- 支持的指标名称；
- 支持的分群维度；
- 支持的过滤字段；
- 时间范围与粒度限制；
- `SUCCESS`、`EMPTY`、`ERROR` 的明确语义；
- 哪些字段需要标准格式；
- 当前调查中哪些能力不可用。

能力描述不能包含：

- 案例 ID；
- Gold 根因；
- 标准证据 ID；
- 观察值；
- 预期查询答案；
- 仅为某个评测案例准备的提示。

### A2. 查询参数规范化

运行时在执行前对工具参数进行规范化，包括：

- `appVersion` 与 `app_version` 等字段别名统一；
- 时间格式统一为 ISO；
- 过滤条件按 schema 排序与去重；
- 维度名称使用工具注册表中的规范名称；
- 明确拒绝工具不支持的参数，而不是模糊返回空结果。

规范化必须基于工具 schema，不能基于案例 ID 或 Gold。

### A3. EMPTY 原因分类

将当前单一 `EMPTY` 拆分为可行动的原因：

| EMPTY 类型 | 含义 | Agent 下一步 |
| --- | --- | --- |
| `NO_DATA` | 查询合法，但窗口内没有数据 | 调整时间范围或停止该方向 |
| `UNSUPPORTED_QUERY` | 工具不支持该指标、维度或过滤 | 使用能力清单改写查询 |
| `NO_MATCH` | 数据存在，但当前过滤组合无匹配 | 放宽或修正过滤条件 |
| `NO_INFORMATION_GAIN` | 查询成功，但没有区分任何假设 | 更换假设判别方向 |

这些分类是 ToolResult 状态或结构化原因，不应伪装成 Evidence。

### A4. 查询意图声明

每次工具调用前，Planner 必须输出一个公开、简短的查询意图：

- 本次查询要区分哪些假设；
- 哪种结果支持哪个假设；
- 哪种结果会反驳哪个假设；
- 如果返回 EMPTY，下一步是什么。

如果查询不能区分任何当前假设，AgentLoop 应拒绝该调用并要求重新规划。

### A5. 语义重复查询保护

除了现有的精确重复签名，还应识别以下低价值重复：

- 只改变参数顺序；
- 使用同义字段名；
- 时间窗口仅轻微变化但目的相同；
- 连续调用相同工具、指标、维度和假设目标；
- 前一次已明确为不支持查询，本次只是换写法重试。

语义重复检测必须基于规范化参数和查询目的，不能使用 Gold。

### A6. 无信息预算

在现有模型调用、工具调用和迭代预算之外，增加独立的“无信息预算”：

- 连续 2 次没有新增 Evidence：强制重新规划；
- 累计 3 次 `UNSUPPORTED_QUERY`：禁止继续同一工具方向；
- 累计 4 次无信息调用：必须选择 `FINALIZE`、`STOP_INCONCLUSIVE` 或请求人类补充信息；
- 无信息预算耗尽不等于技术失败，应保留全部已收集证据。

### A 组验收标准

- EMPTY 比例 ≤35%；
- 精确重复和语义重复调用合计 ≤3%；
- 100% 工具调用都有可审计的假设判别目的；
- 不支持的参数在执行前被拒绝，不被计为正常 `NO_DATA`；
- 关键证据召回不因减少调用而下降。

## 五、改善方案 B：证据充分性协议

### 目标

让 Agent 明确知道“还缺什么证据”和“什么时候可以形成结论”，把证据收集从开放式探索变成可检查的调查计划。

### B1. 建立调查证据清单

每次调查都维护一份服务端可审计清单：

| 证据维度 | 要回答的问题 |
| --- | --- |
| 时间关系 | 异常是否在发布或配置变化后出现？ |
| 暴露关系 | 异常是否集中在新版本、灰度组或受影响配置？ |
| 对照关系 | 未暴露版本、平台或用户群是否保持正常？ |
| 机制证据 | 是否有工具结果或用户反馈支持具体故障机制？ |
| 反证 | 是否存在与当前领先假设冲突的观察？ |
| 替代假设 | 是否检查了至少一个合理竞争原因？ |
| 影响范围 | 受影响指标、平台、版本和用户群是否明确？ |

清单只记录证据覆盖状态，不记录隐藏推理过程。

### B2. 按事故类型定义最低证据组合

不同问题不能使用同一套固定规则。例如：

**发布回归：**

- 必须有时间关系；
- 必须有暴露或版本对照；
- 必须有至少一项机制证据或排除主要替代原因；
- 不能仅凭“发布后发生”认定发布导致。

**配置错误：**

- 必须确认配置或实验组差异；
- 必须定位受影响分群；
- 必须排除全局性外部因素。

**上游依赖：**

- 必须确认跨版本或跨暴露组的一致影响；
- 必须有上游状态、错误模式或历史机制证据；
- 不能把历史相似事件直接当作当前根因证明。

**证据不足：**

- 必须明确指出缺失的数据类型；
- 必须说明为什么现有证据无法区分主要假设；
- 不得输出伪确定根因。

这些规则应基于事故类型和证据类别，不允许读取评测 Gold。

### B3. 证据覆盖状态

运行时维护以下公开状态：

- `MISSING`：尚未查询；
- `PRESENT`：已有支持或反证；
- `CONFLICTING`：证据互相冲突；
- `UNAVAILABLE`：工具无法取得；
- `NOT_REQUIRED`：该类型调查不需要。

Planner 每次选择工具时优先补齐对最终判断最重要的 `MISSING` 项。

### B4. 领先假设与竞争假设比较

在最终化前，Agent 必须对比至少两个未拒绝假设：

- 哪个假设获得更强支持；
- 哪个假设受到反证；
- 两者还缺什么决定性证据；
- 为什么最终选择其中一个，或为什么仍然无法区分。

这不是要求保存私有 chain-of-thought，而是保存简短的公开决策依据。

### B5. 证据就绪门槛

`FINALIZE` 必须同时满足：

- 所有必需证据维度不是 `MISSING`；
- 至少一个假设达到服务端定义的支持门槛；
- 已处理主要反证；
- 根因、影响对象、指标和建议动作均有证据引用；
- 引用属于当前 Run；
- 若存在冲突证据，诊断中必须披露限制。

如果门槛不满足，Agent 只能继续调查、请求用户补充信息或 `STOP_INCONCLUSIVE`。

### B 组验收标准

- 关键证据召回 ≥80%；
- 业务完成率 ≥55%；
- 引用 ID 有效率保持 100%；
- 无依据关键主张不高于 v2；
- 每个 `INCONCLUSIVE` 都包含明确的缺失证据和下一步建议；
- 不能通过放宽 grounding 提高完成率。

## 六、改善方案 C：停止、收敛与最终化

### 目标

减少无意义的长调查，同时避免在关键证据尚未收齐时过早停止。

### C1. 三种停止条件

**形成诊断：**证据充分性门槛满足，领先假设明显优于竞争假设。

**证据不足：**关键证据不可用或预算内无法获得，现有证据不能区分主要假设。

**请求人类补充：**用户可以提供一个明确缺失的信息，例如灰度配置、受影响版本或时间窗口；请求必须具体，不能只是“请提供更多信息”。

### C2. 停止决策由 AgentLoop 校验

Planner 可以提出停止，但 AgentLoop 必须根据以下服务端事实校验：

- 剩余预算；
- 证据覆盖状态；
- 连续无信息次数；
- 是否仍有可用且高价值的工具；
- 是否存在未处理的关键反证；
- 最终输出是否满足 schema。

停止不能完全由模型自由判断。

### C3. 预留最终化预算

避免调查用完全部模型调用后才开始组织结论：

- 至少预留 2 次模型调用给证据总结和格式修复；
- 当剩余预算达到预留线时，禁止发起低优先级新查询；
- 最终化失败时保留证据包，并允许一次有界修复；
- 修复耗尽后以结构化 `INCONCLUSIVE` 结束，而不是丢失整个调查。

### C4. 统一证据包

在最终模型调用前，由运行时生成一个结构化证据包：

- 当前领先假设；
- 主要竞争假设；
- 支持证据；
- 反证；
- 影响指标和分群；
- 缺失或不可用证据；
- 允许的动作类型；
- 审批要求。

模型只能基于该证据包形成最终表达，不能重新引入未收集事实。

### C5. 最终输出质量检查

最终诊断必须通过：

- 根因机制是否明确；
- 受影响对象是否明确；
- 是否区分相关性与因果性；
- 所有关键主张是否引用当前 Run Evidence；
- 建议动作是否与证据和置信等级匹配；
- 是否保留限制条件；
- JSON schema 是否完整。

### C 组验收标准

- 技术完成率 ≥95%；
- `PROVIDER_MALFORMED_RESPONSE` ≤1/66；
- 三轮终态一致性 ≥70%；
- P95 ≤240 秒；
- 平均模型和工具调用不高于 v2；
- 不能用增加预算换取表面完成率。

## 七、改善方案 D：面向 PM 的异步调查体验

### 目标

让 3–5 分钟的调查变成可理解、可离开、可恢复的任务，而不是长时间加载。

### D1. 调查阶段展示

页面只展示用户可理解的公开阶段：

1. 建立竞争假设；
2. 检查发布与暴露关系；
3. 分析受影响指标和用户群；
4. 验证反证与替代原因；
5. 生成诊断与行动建议。

不展示 chain-of-thought，也不把每一次模型调用暴露为用户步骤。

### D2. 支持离开与返回

- 调查启动后立即创建持久 Run；
- 用户可以离开页面；
- 页面刷新后恢复真实进度；
- 调查完成、失败或需要补充信息时发送应用内通知；
- 不依赖浏览器持续打开。

### D3. INCONCLUSIVE 产品化

`INCONCLUSIVE` 不应只是失败提示，应包含：

- 已经确认的事实；
- 尚未确认的内容；
- 当前最可能的两个原因；
- 缺失的决定性证据；
- 用户可以提供的具体信息；
- 继续调查的入口。

### D4. 结果页信息层级

结果页优先顺序：

1. 是否与发布相关；
2. 当前根因及置信等级；
3. 受影响指标和用户群；
4. 最关键的支持证据和反证；
5. 建议动作与风险；
6. 完整调查轨迹；
7. 审批入口。

### D 组验收标准

- 页面刷新后 Run 状态和证据完整恢复；
- 用户可以离开任务并收到完成提示；
- `INCONCLUSIVE` 结果 100% 提供明确下一步；
- 所有外部写入仍需要对单一冻结动作进行明确审批；
- 用户无法通过客户端状态绕过服务端审批。

## 八、改善方案 E：评测与实验设计

### E1. 保留 v2 冻结基线

下一版必须使用新版本号和独立输出目录。不得覆盖：

- v1 正式结果；
- v2 三轮正式结果；
- v2 盲评；
- 误配置和额度失败归档；
- 当前 summary、review queue 和报告。

### E2. 分层验证流程

**第一层：静态与确定性测试**

- 工具能力清单；
- 参数规范化；
- EMPTY 分类；
- 重复查询保护；
- 无信息预算；
- 证据门槛；
- 停止规则；
- 审批和 grounding 回归。

**第二层：小规模诊断集**

选择固定、预先声明的代表性切片，而不是看到结果后挑案例：

- 发布回归；
- 配置问题；
- 上游依赖；
- 证据不足；
- 用户反馈；
- 未知原因。

每类至少一个案例，验证行为方向，不对外声称准确率。

**第三层：完整 Dev 对比**

- 22 个案例；
- 每案 3 轮；
- 与 v2 使用相同模型和预算；
- 独立目录；
- 所有失败进入正式分母；
- 同版本盲评；
- 输出 v2/v3 对比报告。

**第四层：独立 Holdout**

- 新案例在 Harness v3 冻结后才解封；
- 实现人员和 Agent 均不能访问 Gold；
- Dev 调参完成后不再修改 Harness；
- 优先使用独立模型评审，并抽样人工复核；
- Dev 和 Holdout 指标必须分别报告。

### E3. 反作弊要求

禁止：

- 按案例 ID、事故名称或 Gold 内容写分支；
- 删除失败案例；
- 只重跑低分案例并替换原结果；
- 放宽证据 grounding；
- 将 `INCONCLUSIVE` 自动记为成功；
- 将 Dev 结果称为 Holdout；
- 调整 judge prompt 直到分数提高，却不保留旧评分；
- 把工具提示做成案例答案提示。

## 九、推荐实施顺序

### 阶段 0：行为审计与设计冻结

交付物：

- 179 次 EMPTY 的原因分布；
- 33 次 `INCONCLUSIVE` 的停止原因分布；
- 4 次技术失败的完整分类；
- 工具 schema 和能力清单；
- 证据充分性协议草案；
- 下一版评测配置冻结。

退出条件：每一项 P0 改动都有明确问题、假设、指标和副作用。

### 阶段 1：查询信息增益

实施 A1–A6：能力清单、参数规范化、EMPTY 分类、意图声明、语义重复保护和无信息预算。

退出条件：确定性测试通过，小规模诊断验证中 EMPTY 比例明显下降且关键证据召回不下降。

### 阶段 2：证据充分性与停止规则

实施 B1–B5 和 C1–C5。

退出条件：每种事故类型都能稳定区分 `FINALIZE` 与 `INCONCLUSIVE`；所有结论保留 grounding。

### 阶段 3：产品体验

实施持久进度、异步通知、可恢复结果页和可行动的 `INCONCLUSIVE`。

退出条件：刷新、离开、返回、继续调查和审批流程完整回归。

### 阶段 4：完整评测

依次完成确定性测试、小规模诊断、66 次 Dev 对比和独立 Holdout。

退出条件：所有发布门槛和安全门槛通过；否则明确记录失败并继续实验状态。

## 十、Go / No-Go 决策标准

### 可以进入设计合作伙伴 Beta

必须同时满足：

- 技术完成率 ≥95%；
- 业务完成率 ≥55%；
- 严格根因得分 ≥45%；
- 关键证据召回 ≥80%；
- EMPTY ≤35%；
- 三轮终态一致性 ≥70%；
- 引用有效率 100%；
- 审批、安全和 grounding 无回归；
- 至少完成一次独立 Holdout；
- 所有失败案例和限制公开保留。

### 必须继续保持内部 Alpha

出现任一情况：

- 业务完成率仍低于 45%；
- 严格根因得分提升主要来自放宽评分或 grounding；
- EMPTY 降低但关键证据召回同步下降；
- 终态一致性仍低于 60%；
- 通过增加调用预算才获得提升；
- Holdout 明显低于 Dev；
- 出现未审批外部写入或跨 Run 证据问题。

### 不考虑自动处置

即使下一版达到上述目标，也不应立即开放自动回滚或自动创建外部任务。自动处置需要单独的安全评审、权限设计、误操作成本评估和真实生产验证。

## 十一、主要风险与权衡

| 改动 | 可能收益 | 主要风险 | 缓解方式 |
| --- | --- | --- | --- |
| 工具能力提示 | 减少无效查询 | 泄露 fixture 结构或形成答案提示 | 只暴露 schema，不暴露值、Evidence ID 和 Gold |
| 无信息预算 | 降低耗时和成本 | 过早停止，漏掉关键证据 | 与证据覆盖清单联动，不按次数单独停止 |
| 证据最低门槛 | 提高结论可信度 | `INCONCLUSIVE` 可能短期增加 | 按事故类型设置门槛并提供人类补充入口 |
| 最终证据包 | 提高根因表达质量 | 增加一次模型调用和成本 | 预留预算，禁止重新引入未收集事实 |
| 语义重复保护 | 减少绕路 | 错误判断两个查询等价 | 先保守检测，只拦截高置信重复 |
| 异步体验 | 降低等待焦虑 | 掩盖真实延迟问题 | 继续保留 P50/P95 和成本目标 |
| 新 Holdout | 验证泛化 | 建设成本高、样本量有限 | 先小而严格，来源和 Gold 分离治理 |

## 十二、团队分工建议

| 角色 | 主要责任 |
| --- | --- |
| AI 产品经理 | 冻结目标、定义业务完成和事故类型证据要求、设计 INCONCLUSIVE 体验 |
| Agent 工程 | 查询规划、证据覆盖、停止策略和最终化实现 |
| 工具/数据工程 | 工具 schema、能力清单、EMPTY 分类和参数规范化 |
| 评测工程 | 数据治理、回归测试、Dev/Holdout 隔离、盲评和人工复核 |
| 前端工程 | 异步进度、恢复、通知、结果页和审批体验 |
| 安全/后端 | 服务端权限、审批快照、证据边界和外部写入回归 |

产品经理对指标定义和发布门槛负责，但不能单方面修改 scorer 来让结果达标。评测工程对结果完整性负责，但不能参与按案例调参。

## 十三、最终建议

下一版应优先完成三件事：

1. **让每次工具调用都有明确的信息增益目的，并把 EMPTY 从 54.4% 降到 35% 以下。**
2. **建立按事故类型区分的证据充分性协议，让 Agent 知道什么时候可以下结论、什么时候必须承认证据不足。**
3. **把停止和最终化从模型自由发挥改成 AgentLoop 可校验的服务端规则，提升业务完成率和三轮一致性。**

如果这三项做好，ReleaseGuard 才会从“稳定运行的 Agent 演示”进入“能够持续帮助 PM 完成发布调查的产品”。

下一版不应以 80–90% 根因准确率作为短期宣传目标。可信的阶段目标是：先在严格治理的 Dev 和独立 Holdout 上达到 55% 以上业务完成率、45% 以上严格根因得分和 80% 以上关键证据召回，同时保持 100% 引用有效率与零安全回归。
