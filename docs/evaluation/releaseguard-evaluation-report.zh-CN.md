# ReleaseGuard AI 可复现 Agent 评测报告

> 评测版本 0.2.0 · 22 个受治理的离线案例 · 每个系统独立运行三轮  
> 状态：所有结果均来自 `evaluation/results/summary.json`；任何未实际执行的数值都不会被表述为实测结果。本报告严格区分合成 Dev 证据、公开事故复盘资料和企业生产数据。

## 1. 执行摘要

本评测在相同 DeepSeek 模型、数据集、温度、模型/工具预算、超时、重试和单线程条件下，对比一次调用的 Direct LLM 基线、冻结的 Current Agent，以及经过小范围改进的 Improved Agent。评测发现 Current Agent 在修改前存在明显的可靠性和效率问题：结构化决策反复格式错误、长时间执行无信息增益的调查，以及终态不稳定。Improved Agent 的实现变更不针对任何具体案例，包括 DeepSeek JSON Object 响应模式、在总模型调用预算不变的前提下增加一次有界 schema 修复，以及更明确的收敛指令。

权威实测结果位于 `evaluation/results/summary.json`。公开 `/benchmark` 页面读取同一制品生成的构建副本。所有百分比都必须结合原始分子/分母和 Wilson 置信区间解读。

## 2. 项目与评测目标

ReleaseGuard AI 用于调查产品发布是否引发产品指标问题，将只读观察关联到竞争假设，生成基于证据的诊断，并要求所有外部写操作经过精确的人类审批。本评测测试的是离线调查运行时，不测试生产分析集成、企业用户采用情况或业务投资回报率。

## 3. 能力边界

可执行 benchmark 使用 fixture 支撑的 `get_release`、`query_metric`、`segment_metric`、`search_user_feedback` 和 `search_similar_incidents`。它不连接真实生产数据仓库。所有运行均不会执行 GitHub 写操作。产品其他流程中，即使审批和操作执行成功，也只会进入 `WAITING_VERIFICATION`；v17 不包含修复后的自动验证证明。

## 4. 数据集来源与分布

冻结的受治理 Dev 数据集包含 22 个离线重建案例。审计确认，它并不是 22 个独立来源的公开事故：其中 16 个是合成案例，6 个是仓库原生案例。另有一套包含 42 条公开事故复盘的语料库，仅用于检索评测；该语料的摘要可能包含最终根因，因此不会复用为当前事故的 Gold。数据集版本和 Hash 记录在生成的 summary 以及 `evaluation/dataset/SHA256SUMS` 中。

## 5. 答案泄露控制

执行侧只能接收初始异常以及允许观察项的严格投影。Gold、可接受别名、证据角色、类别、难度、来源备注和 scorer 元数据只存在于评测平面。运行时检索不能接收当前案例的事故复盘。该数据集是开发期间可见的 Dev 集，而不是不可见 Holdout；因此，即使实现中不存在按案例 ID、事故名称或 Gold 分支的逻辑，结论的外推范围仍然有限。

## 6. 测试环境与版本

- 修改前源码提交：`aca76ff977e38df48390da10d622768c61e301b1`。
- 初始工作区状态：用户拥有的未跟踪目录 `portfolio/`；评测过程中完整保留并排除。
- 运行时：WSL 2 / Ubuntu 24.04、Node.js 22+、并发数 1。
- Provider/模型：DeepSeek OpenAI-compatible Chat Completions，`deepseek-v4-flash`。
- 温度 0.1；最大输出 5,000 tokens；请求超时 75 秒；传输重试 0 次。
- Agent 预算：总模型调用 20 次、工具调用 10 次、迭代 16 次。

## 7. 基线定义

**Direct LLM** 在一次模型调用中接收相同的初始异常和全部允许的静态观察，不使用动态工具。**Current Agent** 是修改前冻结的 Planner 和共享 AgentLoop。**Improved Agent** 仅调整结构化输出可靠性和收敛行为。没有实现 Fixed Workflow 基线：现有确定性 Harness 只能验证流水线可重复性，不构成可比较的 LLM 调查，将其描述为准确率会产生误导。

## 8. 指标定义与评分

评分规则在 Agent 修改前冻结于 `evaluation/config/scoring.json`。技术完成率、业务完成率、根因得分（2/1/0/N/A）、引用有效性、关键证据召回、无依据主张、实际工具行为、三轮稳定性、延迟、tokens 和估算成本均为独立指标。根因边界案例使用同模型盲审：系统名称被隐藏，输出顺序按确定性规则打乱。但由于 judge 并非独立模型，因此不得将其描述为人工评审或独立裁决。

## 11. 稳定性、延迟、成本与安全

稳定性指标包括首轮技术 Pass@1、三轮全部技术完成、终态一致性、根因得分一致性，以及离线无人工干预执行。“无人工干预”仅表示 Harness 运行期间不需要人类修改状态或输入，不代表已具备企业级无人值守能力。成本按照公开的峰值/非峰值 token 单价估算，并保守地将所有输入视为 cache miss；它是估算值，不是账单。

安全结论仅适用于现有测试。回归套件覆盖精确审批绑定、拒绝未审批完成、冻结参数、重放/幂等、跨运行证据拒绝、仅依赖 RAG 的根因拒绝、无效 Planner/工具决策、原子失败行为和失败状态保留。审计未发现专门的恶意 prompt injection 测试，因此本报告不声称测得了 prompt injection 绕过率。

## 12. 典型成功案例

`summary.json.typicalTrace` 选择了一个盲审根因得分为 2 的真实 Improved Agent 试验，并保留公开 rationale、工具结果状态和证据 ID。第一次 judge 尝试因 HTTP 402 `Insufficient Balance` 失败；充值后单独补跑 judge，198 个匿名输出全部成功评分。失败的首次尝试仍保留用于审计。

## 13. 典型失败案例

Current Agent 同时存在技术格式错误，以及技术执行成功但业务调查未完成的情况。例如 CASE-215 在不同轮次中执行了较长轨迹，终态在 `INCONCLUSIVE` 和 `FINALIZED` 间变化。原始报告完整保留轨迹；该案例没有被删除，也没有用更有利的重跑结果替换。

## 14. 错误分布

Current Agent 出现 9 次 `PLANNER_SCHEMA_ERROR` 和 4 次通用运行时错误。Improved Agent 第 3 轮随后遭遇 Provider 账户余额耗尽：完成前两个案例后，其余 20 个案例失败，其中 19 个是接近即时发生的零调用失败。首次 judge 尝试的 22 个请求也全部返回 HTTP 402 `Insufficient Balance`；该尝试被封存，充值后的完整 judge-only 补跑成功。Agent 第 3 轮失败仍保留在正式分母中，但不得将其归因于 Agent 推理质量。工具结果 `EMPTY` 表示没有信息增益，不是传输失败。

## 15. 产品变更

1. **DeepSeek JSON Object 模式。** DeepSeek 的结构化 Planner 调用请求 `response_format: {"type":"json_object"}`，针对无效/空 JSON，不改变通用 OpenAI-compatible 行为。
2. **第二次有界修复。** 生产和实时评测最多允许两次 schema 修复，仍受总计 20 次模型调用的服务端预算约束。该变更提高可恢复性，但 Provider 持续违反 contract 时可能增加延迟和 token。
3. **收敛策略。** Planner 指令要求：查询相关当前事故来源后，拒绝或降级缺乏支持的推测性备选原因；无信息增益时停止探索。该变更针对无效调用，不改变工具或迭代上限。

聚焦回归测试验证了 JSON Object 模式和修复耗尽路径。修改后的完整运行时测试套件通过。

## 17. 已知限制

- 22 个受治理 Dev 案例样本量较小，开发期间可见，不是不可见 Holdout。
- 6 个仓库原生案例和 16 个合成案例不能代表企业事故的多样性。
- 同模型盲审不是独立裁决；进入队列的项目仍需要真正的人工复核。
- Fixture 工具不能衡量生产 connector 的可靠性或真实数据质量。
- 根据公开 token 单价计算的成本可能与实际账单不同，且不包含工程人力成本。
- 额外中断的 Improved Agent 尝试是运行开销，不属于正式试验。
- DeepSeek 余额耗尽严重污染了 Improved Agent 第 3 轮。后续 judge-only 补跑成功，因此语义评分完整；但评分仍会将冻结的失败试验计为失败，无法消除 Provider 中断对 Improved 对比的混杂影响。

## 18. 复现

参见 `docs/evaluation/reproduce.md`。复现流程会冻结并验证数据集 Hash，运行 Direct 和 Agent 系统，保存 checkpoint，执行盲审，生成 summary 与 review queue，并运行项目验证。凭据始终保存在仓库外部。

## 19. 结论与下一步

本工作将现有 Dev benchmark 转化为可审计对比，同时避免把合成 fixture 错标为公开事故，也不把确定性流水线成功率伪装成 Agent 准确率。当前结果表明，Direct LLM 在该离线 Dev 集上明显优于两代 Agent；Agent 的主要问题包括无信息工具调用、关键证据召回不足、过度 `INCONCLUSIVE`、结构化输出失败和终态不稳定。

下一步可信工作应包括：建立带真实公开来源引用的独立 Holdout；使用独立模型或人工语义裁决；增加明确的对抗性 prompt injection 测试。在获得授权的实时数据集成和前瞻性评测之前，不应作出生产能力或企业准确率声明。
